# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A Chromium extension (Manifest V3) that enhances SAS Studio 3.8 (a legacy Dojo 1.x web app) by monkey-patching in the page's MAIN world. Two main features: toggling SAS Studio's built-in editor for a modern Ace editor at runtime, and various independent UX fixes (formerly a Tampermonkey userscript, now fully absorbed into the extension — nothing to install separately anymore). Everything works by reverse-engineered runtime patching — no build step or bundler for the extension's own code (`./tools/build_lib.sh` only generates the gitignored `lib/`), and `test/smoke.js` is the test suite.

A live SAS Studio instance for testing runs at `http://sas-ue.lan/SASStudio/38/`. **It is rate-limited: run only ONE `test/smoke.js` (or ad-hoc playwright script) against it at a time.** Parallel or rapid-fire runs exhaust its sessions and it starts returning HTTP 503 (then 000 while it restarts) for minutes — serialize your runs and, if you hit 503, wait for it to recover rather than retrying in a loop.

**Do not commit (or push) until the user explicitly asks.** Make and verify changes in the working tree and wait; the user decides when — and to which branch — anything gets committed.

## Components

Everything below lives in one extension, all patching the same app. The repo root is the extension root ("Load unpacked" points at it): `manifest.json` sits at the root, all source files (`sw.js`, `relay.js`, `editor-swap.js`, `ss-fixes.js`, `tools-meta.js`, `defaults.js`, `ace-patches.js`, `popup.html`/`popup.js`, `options.html`/`options.js`, and the custom `ace/` files) live under `src/`, and `assets/` (icons) + `lib/` (gitignored, generated by `./tools/build_lib.sh` — Ace built from source under our own module namespace, ace-linters byte-identical to its npm tarball, plus the built SAS LSP bundle; see `src/ace-patches.js` for why nothing under it is ever hand-edited) stay at the root. Consequences of that split: manifest entries and `chrome.scripting` `files:` lists are extension-root-relative (`src/...`), while `options.html`/`options.js` reference the Ace lib page-relatively as `../lib/...`. `./tools/package.sh` zips exactly `manifest.json src assets lib` into `dist/` (gitignored), running `./tools/build_lib.sh` first if `lib/` is incomplete and leaving out the dev-only rest (docs, `test/`, `tools/`).

- `sw.js` — service worker, five jobs (no `chrome.commands` handler anymore — the editor toggle / native-mouse toggle / browse / command-palette are all in-page `ss-fixes.js` actions with rebindable hotkeys, e.g. editor toggle defaults to `Ctrl+.`, plus the popup's buttons; the only browser command is `_execute_action`, which Chrome itself handles to open the popup, unbound by default). In-page editor toggles post `{ __ssextBadge }` → `relay.js` → a `chrome.runtime.onMessage` listener here that sets the per-tab `ON`/`OFF` toolbar badge (MAIN-world code can't call `chrome.action`; the popup sets its own badge directly):
  1. ss-fixes injection: on every `tabs.onUpdated` for a `/SASStudio/` URL, injects `tools-meta.js` + `ss-fixes.js` into the MAIN world, then pre-injects `editor-swap.js` (+`ace-patches.js`) and seeds `window.__ssExt.libPath`/`userSnippets`/`aceConfig`/`browsePaths` (the latter via `getAceConfig()`, storage merged over `DEFAULT_ACE_CONFIG`), and only THEN calls `window.__ssf.init(settings)` with the persisted patch/hotkey/`keyLayout` settings from `chrome.storage.local` — so the global command-palette / browse hotkeys, any editor created on that page load, and the `aceEditorOnLoad` patch (which toggles Ace on at init and needs `libPath`) all already have what they need.
  2. Live snippet apply: on `chrome.storage.local`'s `snippets` key changing, pushes the new text into every open SASStudio tab via `window.__ssExt.applySnippets`.
  3. Live ace-config apply: on `chrome.storage.local`'s `aceConfig` key changing (written either by options.html or, via `relay.js`, by the in-page settings panel), merges it over `DEFAULT_ACE_CONFIG` and pushes it into every open SASStudio tab via `window.__ssExt.applyAceConfig`.
  4. Live browse-prompt apply: on `chrome.storage.local`'s `browseKeys` key changing (the options page's per-action browse-prompt key overrides, not host-scoped — which key does what isn't a property of the server), assigns it to every open tab's `window.__ssExt.browseKeys`; on `browsePaths` key changing (the popup's per-host root paths), assigns each open SASStudio tab its own host's entry to `window.__ssExt.browsePaths` — no apply function needed, `ext-browse_ss.js` reads it when a prompt opens.
  5. Dark mode: `syncDarkInjection(mode)` registers (or unregisters) a content script with id `ssext-dark` at `document_start` over `*://*/SASStudio/*`, `persistAcrossSessions` — `["src/dark-inject.js"]` for `"on"`, `["src/dark-media-auto.js", "src/dark-inject.js"]` for `"system"`, nothing for `"off"`. `dark-inject.js` attaches `src/dark.css` as a **`<link>` node it creates**, NOT as a registered `css:` entry, and that distinction is the whole design: extension-injected CSS lands in a separate injection origin that is neither in the page's `document.styleSheets` nor removable by `chrome.scripting.removeCSS` (which only tracks `insertCSS`'d sheets), so once in it could never be taken out and turning dark mode off needed a reload. Both were verified against the live app. A `<link>` is an ordinary DOM node, so `applyDarkToTab(tabId, mode)` can add/replace/remove it in any open tab and every transition is live — on, off, and on↔system — with Ace re-themed in the same pass so the editor and app chrome never disagree. The ace-built overlays come along too, via `editor-swap.js`'s `syncOverlayDefaults()` (called from `loadNewAce()`, from `applyAceConfig()` — which `sw.js` runs on every dark-mode change — and from one page-level `matchMedia` listener, since a prompt can be opened with no editor open): the command palette prompt, browse_ss and the stock settings menu are plain divs on `document.body` whose inner editors are created with NO theme (so they take ace's default) and whose containers ace styles `background: white`. It points ace's default editor theme at whichever of our two themes is current (our SAS editors pass a theme explicitly, so they are unaffected) and toggles a `ssExtDark` class on `<body>` that the static `#ssExtDarkOverlays` sheet keys off. It also points ace's default editor FONT SIZE at `aceConfig.options.fontSize`: ace's own default is 12px, a squint next to a 15px editor, and the palette's input only takes the focused editor's size when there IS one - its completion list (and both, when the palette opens with nothing focused) fall back to the default. `ext-browse_ss.js` reads the same configured size for its own prompt/popup instead of the 14/15 it used to hardcode. That sheet also sets `color-scheme: dark` on `#ace_settingsmenu`/`#kbshortcutmenu`: the settings panel is a plain `<table>` of NATIVE controls (ace's own `.ace_optionsMenuEntry` rules match nothing in the DOM `OptionPanel` builds), and a `background-color` on a `<select>` computes but is never painted — Chromium draws the platform widget — so the platform has to be told to draw it dark. Buttons and text inputs still need explicit colours: something in the page paints them white, which with the panel's light text leaves the labels invisible. (This is how Dark Reader itself toggles live: it appends its own `<style class="darkreader">` nodes and removes them again.) `"system"` is the `media` attribute on that link, which is why there is only ever ONE copy of the stylesheet. Appended to `documentElement` (at `document_start` `<head>` may not exist yet); a stylesheet in the document blocks rendering until it loads and this one is a local extension resource, so the first paint is already dark — measured frame-by-frame via a CDP screencast, 0 light frames in 157 across a 6.3s load, against a dark-mode-off control that shows 22.

- `relay.js` — ISOLATED-world content script (`*://*/SASStudio/*`, `manifest.json`'s `content_scripts`), the only bridge from MAIN-world code to `chrome.storage`: listens for `window.postMessage({ __ssextAceConfig: config })` (source-checked) and writes it to `chrome.storage.local.aceConfig`. Nothing else.
- `editor-swap.js` — defines `AceEditorAdapter` (full reimplementation of the `SAS.Editor` API on top of Ace) and the `window.__ssExt` singleton (`active`, `activate`, `deactivate`, `toggle`, `loadNewAce`, `browse`, `commandPalette`, `applySnippets`, `applyAceConfig`, `libPath`, `aceConfig`). `commandPalette(libPath)` (libPath optional once `ssExt.libPath` is already known — see the global hotkey path below) serializes through the same `_pending` chain as `toggle`/`browse`: it determines the currently-focused Ace editor *before* opening anything (`focusedAceEditor()` — checks `_textViewers` first, then `appDMS.tabs.getAllTabObjects()` code tabs, via each candidate's `.isFocused()`), then `loadNewAce()`s and calls `openCommandPalette(focusedEditor)` with that editor (or `null` if nothing was focused). The adapter's own in-editor `openCommandPalette` command (Alt-Shift-P) calls the same function with `this.aceEditor`. `openCommandPalette` is built on the stock, vendored `ace/ext/prompt` module (`lib/ace/src-noconflict/ext-prompt.js`) rather than a custom prompt module: it builds an entries array — always `SS-Ext: <label>` entries (one per `SSF_TOOLS` action — which now includes `toggleEditor` and `toggleNativeMouse`, so no special-casing) and, only when a focused editor was passed, that editor's own commands (walking `editor.keyBinding.$handlers`, deduped by name, mirroring `prompt.commands`'s `getEditorCommandsByName`, excluding `["insertstring","inserttext","setIndentation","paste"]`) — plus a side-table of runner functions keyed by each entry's `command` field (needed because `prompt.commands`'s `getCompletions` JSON-clones the entries on every filter, which would strip functions), then calls `ace.require("ace/ext/prompt").prompt(focusedEditor || null, "", { name: "commands", selection: [0, Number.MAX_VALUE], onAccept, getPrefix, getCompletions })`, copying `getPrefix`/`getCompletions` filtering from that same preset. The palette keeps a command history (`SsCmdPaletteHistory` in `chrome.storage.local`, relayed via `relay.js` — global/unprefixed since command names are server-agnostic — an MRU list of `entry.command` keys, cap 5, recorded in `onAccept`): entries on the list are moved (deduped, not copied) to the front of the entries array in MRU order, so the last-run command is the pre-selected first row on reopen; the popup displays `getCompletions`' return order (`FilteredList.filterCompletions` filters without sorting), so matching recents stay on top while typing too. History only reorders entries present in the current list, so editor-only commands in the history never appear in the global (no-editor-focused) palette. A global in-page hotkey (default Alt+Shift+P, rebindable like any other `ss-fixes.js` action — see the `commandPalette` entry in `SSF_TOOLS`) opens the palette even with Ace not activated and nothing focused: `sw.js`'s `tabs.onUpdated` handler pre-injects `editor-swap.js` and seeds `ssExt.libPath`/`ssExt.userSnippets` on every SASStudio page load, so the no-arg `window.__ssExt.commandPalette()` call has what it needs to load the Ace lib on demand. The popup's "Command palette…" button is an alternative entry point, passing an explicit `libPath` (there is no chrome command for it anymore — the only browser command is `_execute_action`, which opens the popup). On first injection it installs one-time dispatcher patches: `SAS.Editor` becomes a function returning either an `AceEditorAdapter` or the original editor depending on `__ssExt.active`, and `DMSEditor.prototype.createCodeEditor` is wrapped the same way (original saved on `__ssExt`, guarded by `_aceReplacementPatched`). `loadNewAce()` loads the newer Ace library from `lib/ace/src-noconflict/` once, onto `window.__ssAce`: `tools/build_lib.sh` builds ace from source with its module-registry namespace set to `__ssAce` instead of `ace` (see its comment), so the two ace libraries on the page have separate registries and SAS Studio's own 1.x build keeps `window.ace` — and its own stock editor — entirely to itself. Nothing swaps, pins or restores a global, so a lazily loaded keybinding/theme/mode cannot land in the wrong library in either direction (which is how vim's `:w`/`:q`/`:wq`/`:x` once silently vanished), and because SAS's stock editor still tokenizes against ITS ace, bumping `ACE_VERSION` cannot break it and needs no compat shims. `editor-swap.js` keeps our library in one closure variable (`ace`, assigned from `window.__ssAce` in `doLoadNewAce`), `options.js`/`ace-seed.js` do the same, and `src/ace/*.js` (our own ace modules) carry the `__ssAce.define`/`__ssAce.require` names in their source. `ss-fixes.js`'s `init()` calls `loadNewAce()` at page load (after `waitForElm(".dijitTreeNode")`), with the toggle still off; `toggle`/`browse`/`commandPalette` call it too and it is memoized on the in-flight promise (`ssExt._loading`), since the page-load call sits outside their `_pending` chain. Our CSS stays attached permanently — SAS Studio renders its own editor DOM via EditorView.js and never references any `.ace_*` class, so the vendored ace's own styles are inert either way. Before loading it, `dropOldAceStyles()` removes every pre-existing `<style id="ace*">`/`#vimMode` element — the ones SAS's own 1.x ace injected as a side effect of `SyntaxColorerAdapter.js` importing it for `EditSession` (SAS itself needs no ace CSS: its editor DOM is EditorView.js's own markup): ace's `importCssString` dedupes by element id, so any id SAS registered first would silently drop OUR version, and the new build inserts its styles at the top of `<head>`, leaving the old ones later in the cascade. `loadNewAce()` also injects one `#ssExtVimCursorFix` override sheet — some themes style `.ace_cursor` at the same specificity as `keybinding-vim`'s `.normal-mode .ace_cursor` rule and load after it, killing the vim block cursor (`theme-github_light_default`'s `background: none`; `theme-ambiance`'s `.ace-ambiance.normal-mode .ace_cursor-layer{z-index:0}` hides it behind the marker layer instead). `activate()`/`deactivate()` no longer touch the `window.ace` global at all (see `loadNewAce()` above — the replacement is permanent); they just walk every open tab converting its editor in place and re-binding `textChanged`/`selectionChanged`/`caretMoved`. Undo history does not survive a toggle in either direction. `browse(kind, libPath, snippetsText)` (used by `window.__ssExt.browse` for browse_ss prompts) only calls `loadNewAce()`, not `activate()` — it works without activating the editor replacement. `applySnippets(text)` registers the user's custom Ace snippets (`ace/snippets` snippetManager, additive over the built-in set) — no-op until the new Ace lib is loaded. `loadNewAce()` also calls `registerOtherEditorsCompleter()` (guarded by `ssExt._otherEditorsCompleterAdded`), which `addCompleter`s one extra completer (id `ssextOtherEditors`) onto `ext-language_tools`' global completers array — ace's built-in text completer only ever looks at the CURRENT session, so this one harvests the words of every OTHER live adapter (`allAdapters()`, the shared text-viewers-then-code-tabs walk `applyAceConfig` uses too). Words are cached per session in a `WeakMap` and dropped on that session's `change` (one listener per session ever — the entry object stays, only its `.words` is cleared), since splitting every other tab's full text on every keystroke of live autocompletion is otherwise the cost. It has to be registered before any editor exists: `_maybeRegisterLsp` replaces `editor.completers` with its own copy, which a later `addCompleter` can't reach. Its entries score 0 — below the local text completer's distance-based scores, and far below the LSP's. A second completer (`ssextSasContext`, registered the same way) covers what the SAS language server cannot answer, from the same library tree as `sas/getLibList`: (a) **PROC SQL data set names** — inside `proc sql;` every caret position is zone `PROC_STMT_OPT` and the server only offers the SELECT statement's option NAMES, because its syntax data types the `FROM` option as `"value"`, not `"dataSet"`, so `isDataSetType()` never fires and no library list is ever requested (verified against the language service directly for from/join/create table/insert/update); (b) **column names** — the server has no column zone at all (`getDocumentVariables()` is a `//TODO:` stub), so `keep `, `var `, `select `, `where ` get nothing. `stepAroundCursor(session, pos)` cuts the step out of ±200 rows around the caret — it must reach PAST the caret, since `select | from sashelp.class` names its table after it — bounded by the last `proc`/`data` behind and the next `run;`/`quit;`/`proc`/`data` ahead (a `run;`/`quit;` BEFORE the caret means the step is over and nothing is in scope). `tableRefs(step)` pulls `{lib, table, alias}` out of `from`/`join`/`into`/`update`/`table`/`set`/`merge`/`data=`, where only the SQL keywords take an alias (`from a.b x` aliases, `set a b` is two data sets) and a `NOT_A_TABLE` stop-word set keeps `where`/`on`/`end=` out. Columns are resolved BY NAME through the two cached listings (`@libs` → that library's tables → that table's tree id → its columns), so no tree path is ever built by hand, and served from `columnsByRef` synchronously while `warmColumns()` fills it in the background — the popup never waits on a round trip, results land a keystroke later (and warming is skipped while `window.__ssfRunDialog` shows a run in progress, since that request would just queue behind the program). Columns are offered step-wide rather than after an allowlist of clauses (case-when, function arguments, `calculated`, data-step expressions — an allowlist misses more than it saves), except at the start of a statement, where a statement keyword belongs. A `name.` before the caret scopes them to that TABLE; SQL aliases are parsed (so `from a.b x` doesn't invent a table `x`) but deliberately not resolved, so `x.` offers nothing rather than a guess. Its entries score 1000, above the LSP's 0. `appDMS.createFileView` is also wrapped once (`_createFileViewPatched`): while active, the "View file as text" viewer gets a read-only `AceEditorAdapter` overlay (registry in `__ssExt._textViewers`) laid over the real `SimpleTextarea`, which is kept alive in the widget tree (just visually hidden) so AppDMS's positional load/refresh code (`AppDMS.js:3931`/`3985`, which indexes `pane.getChildren()[1].getChildren()[0]` rather than going through `tabHolder.simpleTextArea`) keeps working untouched; the widget's `.set("value", ...)` is patched to also mirror writes into Ace. The overlay is always editable; a real edit marks the tab dirty (`*name` in the tab title, matching `DMSEditor.applyChangedIndicationToTab`) and enables saving. Save is wired three ways — a toolbar `Save` button (TXT/LOG only), `Ctrl/Cmd+S`, and vim `:w`/`:wq` — all POSTing the edited text to the workspace endpoint (mirrors `DMSEditor.saveFile`'s plain-file path); vim `:q`/`:wq` also close the tab. `:w <path>` (a path argument on the ex-command) instead routes to `ss-fixes.js`'s `saveFocusedFileAtPath(path)` — the same save-as-at-path flow as the `saveFileAtPath` action, factored out so both share it. `:x` is remapped off the stock save-and-close to instead invoke the `runCurrentProgram` ss-ext action (also in `SSF_TOOLS`/the command palette), submitting the focused editor's program or selection like F3. The vim ex-commands are registered once on the shared `ace/keyboard/vim` module and resolve the acting `cm.ace` back to either a text-viewer entry or a code-editor tab, so they work in both. `installVimExCommands()` loads `keybinding-vim.js` with the plain `loadScript()` helper and is AWAITED inside `loadNewAce()`, so the ex-commands and the vimrc are registered before it resolves (historically this also had to dodge the shared-`ace`-global problem — the file registered itself through whatever `window.ace` pointed at, which for a browse/palette-before-activation load was SAS's build, and the `defineEx` calls silently never ran; the namespace rename removes that failure mode). `deactivate()` disposes the adapter, clears the dirty marker, unhides the textarea, and restores its original `.set`; viewers opened while inactive are unaffected. (Note: `loadNewAce()` overrides the module URL for `ace/keyboard/vim`/`emacs`/`sublime`/`vscode` to `keybinding-<name>.js` — this build otherwise resolves them to a 404, which had silently disabled non-Ace keyboard handlers entirely.) Persistent editor config: `ssExt.aceConfig` (`{ darkTheme, lightTheme, options, vimrc }`, seeded by `sw.js` and refreshed by `applyAceConfig(config)`) backs `getAceConfig()`, which the adapter constructor reads for its initial theme/`ace.edit()` options, and which `applyConfig(cfg)` (an adapter method) re-applies live (theme via the existing matchMedia machinery — `this._darkTheme`/`_lightTheme` are read live by the matchMedia handler, not captured at construction — plus `aceEditor.setOptions(cfg.options)`). `applyAceConfig(config)` stores it on `ssExt.aceConfig`, calls `applyConfig` on every open adapter (code tabs + `_textViewers`), and (if `config.vimrc` changed since the last apply) reapplies vimrc — see below. `sw.js` calls it on `aceConfig` storage changes. There is no custom preferences panel: Ace's own stock settings menu (`showSettingsMenu`, default `Ctrl-,`/`Cmd-,` command, also surfaced generically in the command palette's per-editor commands list whenever one is focused) is THE settings UI. Loading `ext-settings_menu.js` (in `loadNewAce()`, replacing what used to be a separate `ext-options.js` load — that file bundles its own copy of `OptionPanel`, so eagerly loading it makes the stock command's lazy `config.loadModule("ace/ext/settings_menu", ...)` a no-op, not a second HTTP load) is enough for the menu to work at all; `installSettingsMenuPersistence()` (called once per `loadNewAce()`, guarded by `ssExt._settingsMenuPatched`) additionally patches `ace.require("ace/ext/options").OptionPanel.prototype.setOption` so panel changes stick: after the original runs (which already fires the panel's own `"setOption"` signal), if `option.path` isn't `"theme"`/`"mode"` it updates `ssExt.aceConfig.options[option.path]`, live-applies via `applyAceConfig`, and `window.postMessage({ __ssextAceConfig: cfg }, "*")`s it for `relay.js` to persist (theme is options-page-only, see below; "mode" isn't part of the persisted config). `options.js` installs the identical prototype hook (guarded by its own flag) for the snippet editor's settings menu, writing straight to `chrome.storage.local.aceConfig` instead of postMessage-ing. `loadNewAce()` also calls `installDialogFocusPriorityPatch()` (guarded by `ssExt._dialogFocusPatched`), which patches `dijit.Dialog.prototype.show`/`focus` so an open SS-Ext prompt (the command palette's `.ace_prompt_container` or browse_ss's `.ace_browse_ss_container` — both plain z-index overlays with no native focus trap) keeps focus over SAS Studio's dijit dialogs: dijit's `show()` autofocus is skipped while a prompt is open, and `Dialog.prototype.focus()` (the `focus.watch("curNode")` trap that yanks focus back inside the top dialog whenever it leaves) no-ops when the live focus is already inside our prompt. Without it, opening Save As (or any dijit dialog) over the palette would immediately steal focus back to the dialog's first field, freezing the palette. `installResizablePopups(ace)` (guarded by `ssExt._resizablePopupsPatched`) makes every ace popup resizable, with the `RESIZABLE_CSS` sheet supplying the handles: `resize: both` on `.ace_editor.ace_autocomplete`, `resize: horizontal` on the two prompt boxes (`div.ace_prompt_container` here, `.ace_browse_ss_container` in `src/ace/ext-browse_ss.js`, both given a plain `width` instead of ace's `max-width` + `width:100%`, since a max-width would clamp the drag) and `resize: vertical` on the list inside a prompt. The split is forced by ace's own CSS: `.ace_editor.ace_autocomplete` is `position: absolute`, so a prompt's completion list isn't laid out inside the white box at all (which is why the box can't grow to it, and why the list's `width:100%` is 100% of the full-screen overlay and is sized in practice by the inline `max-width` the prompt sets) — hence one handle per axis, with the box's width mirrored onto the list's inline `max-width`. CSS alone isn't enough either: ace re-derives an autosizing editor's height from `$maxLines` on every render, so a `ResizeObserver` turns a dragged height back into `$maxLines` (plus `$minLines` for prompt lists, so a short list still fills the dragged box; the editor's own popup gets only the cap, since a tall empty box at the caret is just in the way), keyed off `clientHeight` differing from ace's own `desiredHeight` by more than a line. It hooks `VirtualRenderer.prototype.$autosize` rather than wrapping `AcePopup`, because both `ext-language_tools` and `ext-prompt` capture `AcePopup` in a module closure when they load — long before `loadNewAce()` could reach the export — and `$autosize` is the one place that runs per popup render AND has the renderer to hand the observer. `ssExtCompletionPopup`'s 400px width rule uses a doubled class rather than `!important` for the same reason the rest of this avoids `!important`: an author `!important` would beat the inline width a drag writes. A dragged prompt size is remembered in `promptSizes` (module-level, by box class name, page session only — every open builds a fresh popup element) and restored on the next open; a detached/hidden popup (`clientHeight`/`clientWidth` of 0) is skipped so closing a prompt can't save a junk size.

SAS language server (LSP): `ensureLsp()` lazily starts one shared ace-linters `LanguageProvider` for the whole page, memoized on `ssExt._lspStarting` (a failure sets `ssExt._lspFailed` so it's never retried until reload). It bails to `null` if `getAceConfig().lsp === false` (the options page's "SAS language server" checkbox, `aceConfig.lsp`, default on); otherwise it derives the extension root from `ssExt.libPath` (same suffix-strip pattern as `srcAcePath`), `fetch(..., { method: "HEAD" })`-probes `lib/sas-lsp/sas-server.js` (console.warn + `null` if the gitignored bundle hasn't been built by `./tools/build_lib.sh`), loads `lib/ace-linters/language-client.js`/`ace-language-client.js` as classic scripts (temporarily deleting the global `window.define` around the load — Dojo's own AMD loader satisfies the UMD wrapper's `typeof define === "function" && define.amd` check and would register the module into Dojo's registry instead of setting `window.LanguageClient`/`window.AceLanguageClient`), then constructs the worker as `new Worker(URL.createObjectURL(new Blob(["importScripts(...)"])))` pointed at the server bundle (blob+`importScripts`, not a fetched string, to avoid holding the ~22 MB bundle in memory as JS source) and calls `window.AceLanguageClient.for(serverData, { functionality: { completion: { overwriteCompleters: false }, semanticTokens: true } })`. `serverData` also carries `initializationOptions: { supportSASGetLibList: true }`: without it the server never wires up its lib service (`server.ts`'s `onInitialize` → `setLibService`) and library/table names are simply absent from completion. With it, the server sends a CLIENT-bound `sas/getLibList` request (`{ libId }` — `null` means "list the libraries", otherwise "list that library's members") and expects `LibCompleteItem[]` (`{ id, name, type: "DATA"|"VIEW"|"LIBRARY" }`) back. ace-linters exposes no way to register an inbound request handler, and its own connection would answer `MethodNotFound` before an async reply could land (first response wins), so the same `onmessage` shim answers it and does NOT forward the message. `getLibList(libId)` reads SAS Studio's own `appDMS.libraries.treeModel.query("libraries" | "libraries~<LIB>")` — the source `src/ace/ext-browse_ss.js` browses, whose child ids come back in that same `~` form, so a library's id round-trips straight back as the next `libId` — memoized in `libListCache` (a failure is never cached; a missing `treeModel` resolves `[]` rather than leaving the request hanging, which would stall that completion forever). `installLibListInvalidation()` wraps `appDMS.libraries.onRefresh`/`refreshTree` to clear that cache (and the column caches with it): SAS Studio refreshes its library tree at every run end (all of `DMSEditor`'s submit paths call `libraries.onRefresh()`, some gated on the `autoRefreshLibraries` preference), on every library add/delete/rename and the Refresh button (`refreshTree()`), and on session reset — hooking both funnels beats a TTL, with no stale window and no polling (`onRefresh` self-gates on `treeViewActive` internally, hence wrapping both rather than relying on it reaching `refreshTree`). Every completion the server sends back is kinded `Folder` for a library and `Keyword` for EVERYTHING else — tables, data set names it parsed out of the program, plain keywords (`CompletionProvider.getItemKind`) — and ace-linters turns the kind straight into the popup's right-hand column, so they read "Folder"/"Keyword". `installLspMetaLabels(editor)` patches that completer's `getCompletions` IN PLACE (not a wrapping copy — ace-linters keeps finding the object by id, e.g. `setServerCapabilities` assigning `triggerCharacters` onto it) and `relabelLspCompletions` rewrites the meta where it can tell what an entry is: `Folder` → `library`; `Keyword` whose name is a known table of the libref typed before the caret → `SASHELP.`; `Keyword` in a response that ALSO lists libraries → `program`, since that is the one response where the server mixes the program's own data set names in. Table names run to 32 characters and ace's popup gives the meta `flex: 0 0 auto` (the CAPTION ellipsizes to make room for it, not the other way round), so `tableMeta()` caps ours at 12 characters and `loadNewAce()` widens the popup to 400px with an `#ssExtCompletionPopup` sheet (`!important`, because `importCssString` PREPENDS to `<head>` and would otherwise lose the tie with ace's own 300px rule) - scoped away from `.ace_prompt_container`/`.ace_browse_ss_container`, whose lists size to their prompt box with an inline `width:100%` that an `!important` rule would otherwise beat, leaving the list narrower than the input above it. Two load-bearing workarounds ported from a standalone sas-lsp demo: (1) ace-linters 2.2.0's `filterByFeature` checks `capabilities.hoverProvider == true`, but the SAS server advertises the object form, so hover silently never fires — a `Object.defineProperty(worker, "onmessage", ...)` shim (an `addEventListener` wrapper sees the message too late) coerces object-form `hoverProvider`/`documentHighlightProvider` to `true` in the initialize response and sets `ssExt._lspReady = true`; (2) with `overwriteCompleters: false` ace's own completers stay registered alongside the LSP one, and the popup sorts by score, so each default completer's `getCompletions` is wrapped to subtract `1e6` from every result's score so LSP entries sort first. It registers the created Ace editor on the resolved provider (also guarded by a `this._disposed` flag set in `dispose()`, in case the adapter was torn down before the promise settled), and schedules the demo's 2-second post-register semantic-token kick (`languageProvider.$getSessionLanguageProvider(session).getSemanticTokens()`, try/catch — the initial request races the server's `didOpen`). The code editor is constructed with empty content and its real text arrives later via `setText()` (text viewers/toggle conversion pass content at construction instead) — `setText()` re-runs the eligibility check after setting the value: if now registered-but-over-the-limit it unregisters (`ssExt._lspProvider.unregisterEditor(this.aceEditor, true)`, clears `_lspRegistered`, logs one `[SS Ext]` line); if not registered and now eligible it calls `_maybeRegisterLsp()` again. Typing growth past the limit after that isn't monitored (a `// ponytail:` comment on the spot notes it — a reload or another `setText` picks it up). `dispose()` calls `ssExt._lspProvider.unregisterEditor(this.aceEditor, true)` (closes the document server-side) before `aceEditor.destroy()`. The worker/provider persist for the whole page lifetime once started — deactivating/reactivating the Ace toggle just re-registers editors against the same one, nothing tears it down. Three more perf workarounds, applied once per page by `installLspMarkerPatches(provider, session)` (called right after the first successful `registerEditor`, guarded by `ssExt._lspMarkerPatched`, patching the prototype of ace-linters' `SessionLanguageProvider` reached through `provider.$getSessionLanguageProvider(session)`) — all three are about semantic tokens, which the SAS server answers for the WHOLE document (`semanticTokens/full`) on every edit and every scroll: (1) `setSemanticTokenMarkers` filters the token set to the viewport ± `SEMANTIC_TOKEN_MARGIN` (50) rows before ace-linters turns each token into an ace text marker — only rendered rows can ever show one, yet `$applyTextMarkers` (which runs on EVERY render) walks the whole set, which measured ~8000 markers created+destroyed per keystroke and 10-60 ms of main-thread work per render on a 1200-line file; Four post-processing steps, each of which exists because of a bug that actually happened:
  1. Strip every `ace_` rule.
  2. Drop every `background-image: url(...)` declaration. Dark Reader's export mixes absolute URLs (baked to whatever host it ran against) with relative ones (relative to the sheet they came from, e.g. `sasIcons/sasdark/`, which resolve against the page root in our sheet — `.dijitTreeIcon` ended up pointing at `/SASStudio/38/16_png/*.png` and 404ing). Dropping the declaration lets SAS Studio's own rule apply, correctly resolved.
  3. Mark colour declarations `!important` (an allowlist — `background-color`, `color`, `border-*-color`, `box-shadow`, …). Chrome injects content-script CSS into the author origin but BEFORE the page's stylesheets, so a same-specificity rule loses every tie: without this, `html`'s background went dark (that rule already had `!important`) and `body`'s didn't. Deliberately NOT applied to `border-width`/`border-style`/`background-size`/`background-repeat`, which would start overriding the inline layout styles Dojo writes on its widgets.
  4. Emit the icon rule. SAS ships BOTH dark artwork (`sasIcons/sasdark/*`, for a light background) and light artwork (`sasIcons/saslight/*`, already for the dark blue banner), so it measures each image's mean luminance on a canvas and inverts only the dark ones — a blanket invert turned the banner's white glyphs into black blobs. The walk MUST run before `DarkReader.enable()`: afterwards it reads Dark Reader's rewritten sheets, every image fails to load, and everything silently measures "not dark" (there's a guard that throws if zero dark icons are found). ## Development

No build step for the extension's own code, no Tampermonkey needed anymore; `./tools/build_lib.sh` generates the gitignored `lib/` (run once after cloning, and after bumping a version variable at its top). Bumping `ACE_VERSION` rebuilds ace from that tag with the namespace patch applied (`git apply` fails loudly if the patch no longer fits, and ace's own build sanity-check loads every file under the new namespace). SAS Studio's stock editor runs against its OWN ace, so an ace bump can't break it — `node test/smoke.js`'s "our ace and SAS's are two separate libraries" / "a lazily loaded module registers in OUR registry" / "SAS's stock editor still resolves everything it needs from its OWN ace" checks are the guards. Dark mode for SAS Studio's own UI is a generated static stylesheet — `node tools/gen-dark-css.js` rewrites `src/dark.css` (needs a live instance and npm; the output is committed, so this is only for re-tuning the palette or tracking a SAS Studio CSS change). Pure-logic checks (no browser, no live instance): `node test/units.js` — covers `tools-meta.js`'s `ssfEventKey`/`ssfPatchEnabled`. Smoke test: `node test/smoke.js` — launches headless Chromium with the unpacked extension against the live instance and exercises injection, middle-click close (raw CDP input — catches event-suppression bugs synthetic dispatch can't), reopen, the native-mouse toggle, Ace activation/deactivation, the text viewer (mirroring/dirty/save/vim), the command palette (focused/unfocused/global hotkey), LSP completion (library/table names from `sas/getLibList`, ranking, cache invalidation, meta labels), cross-editor word completion and the SAS context completer (PROC SQL tables, columns), the aceConfig flow (seeding, live apply, settings-menu persistence via relay.js, vimrc), and dark mode (live apply without a reload, survives a reload, icons still render with no 404s, icon-button labels stay hidden — i.e. `dijit.css` is intact, which is the exact symptom a runtime dark-mode extension kept producing — the stylesheet is a page-owned `<link>` rather than extension-injected CSS, Ace forced onto its dark theme by `"on"` and back off with it, follow-system gated by the link's media attribute, and clean removal both live and after a reload); see the file header for `SS_URL`/`CHROME_BIN` env vars and the playwright requirement. **Run it single-threaded** — the live instance is rate-limited (see top of file), so never launch two runs at once. Concrete recipe when `playwright` isn't a normal dependency here (it usually isn't — it's pulled via `npx`): point `NODE_PATH` at a cached npx playwright and `CHROME_BIN` at the matching cached Chromium, e.g. `NODE_PATH=~/.npm/_npx/<hash>/node_modules CHROME_BIN=~/.cache/ms-playwright/chromium-<build>/chrome-linux64/chrome node test/smoke.js` (find the two paths with `ls ~/.npm/_npx/*/node_modules/playwright` and `find ~/.cache/ms-playwright -name chrome -path '*chrome-linux64*'`; the file header explains the version-match caveat and why a real `google-chrome` won't load the extension headless). Ad-hoc one-off checks (a throwaway playwright script under a scratch dir) run the same way — one at a time. To test changes manually: `chrome://extensions/` → reload the unpacked extension (loaded from the repo root) → refresh the SAS Studio page → toggle with `Ctrl+.` (or the popup's toggle button). To build the publishable zip: `./tools/package.sh` → `dist/sas-studio-ext-<version>.zip` (dist/ is gitignored; it packs `manifest.json src assets lib` — rebuilding `lib/` first if incomplete — so a new runtime file belongs in one of those). All extension logs are prefixed `[SS Ext]`; expect one line per toggle (`activated`/`deactivated ... N tab(s) ...`) plus errors/warnings only.

## Commit convention

Follow the EU Component Library convention
(https://ec.europa.eu/component-library/v1.15.0/eu/docs/conventions/git/):

```
<type>: <subject>

<body>

<footer>
```

No scope — type only. Header mandatory, lines <= 100 chars. Subject in imperative
present tense, no leading capital, no trailing period; body same style,
explaining motivation and contrast with previous behaviour. `BREAKING CHANGE:`
and closed-issue links go in the footer. A revert is `revert: <original header>`
with `This reverts commit <hash>.` in the body.

Types:

- `feat` — a new feature
- `fix` — a bug fix
- `docs` — documentation only
- `style` — formatting/whitespace, no code-meaning change
- `refactor` — neither fixes a bug nor adds a feature
- `perf` — performance improvement
- `test` — adding missing tests
- `chore` — build process or auxiliary tool changes

Do not append session/trailer links to commit messages.
